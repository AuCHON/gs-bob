# Quality Gate（对抗式开发质量门）

> 让 AI 写代码，再派独立的"敌方" AI 来攻击它——修到攻不破，才算完成。
> 工具中立：Claude Code / Cursor / Codex / 任意 AI 编码工具或纯对话均可使用。

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![skills.sh](https://skills.sh/b/ospops/quality-gate)](https://www.skills.sh)

## 这是什么

一套可复用的 **AI 对抗开发质量门**：两层对抗、审查者只读、修复循环直至 PASS。

```
需求（任务）
   ↓
【需求对抗】requirement-adversary ── "这个需求有没有漏洞？"
   ↓
修正需求 → 开发
   ↓
自测门（类型检查 / 测试 / 构建，按仓库实际）
   ↓
【实现对抗】implementation-adversary
   ├─ 代码审查        ├─ 边界攻击        ├─ 异常攻击
   ├─ 数据攻击        ├─ 并发攻击        ├─ 安全攻击
   └─ 自动化测试
   ↓
汇总报告 → 发现问题？
   ├─ 是 → 修复 → 重新实现对抗（循环）
   └─ 否 → PASS → 才向用户汇报"已实现且已通过对抗审查"
```

## 核心理念

1. **实现者不能既当运动员又当裁判**——审查由独立上下文的只读 AI 承担；
2. **抽象层级对齐**：需求层 → 需求对抗；实现层 → 实现对抗（两个角色，不再多拆）；
3. **审查者绝不修改代码**：只读分析、只返回结论；修复永远由主 Agent/人完成；
4. **结论必须可复现**：文件:行号 + 触发条件 + 预期 vs 实际，猜测标注"疑似"；
5. **PASS 有硬标准**：🔴/🟠 全部修复并重审通过 + 全量测试全绿（快套件连续 3 次，
   慢套件 1 次并注明；迭代轮次只跑定向测试）。

## 快速开始（按你的工具）

| 工具 | 接入方式 | 指南 |
| --- | --- | --- |
| **任一支持 skills 的工具**（Claude Code / Cursor / Codex 等） | `npx skills add ospops/quality-gate`（自动映射各工具目录；会读 `.agents/skills/` 的工具零配置） | [skills.sh](https://www.skills.sh) |
| Claude Code | 手动拷入 `.claude/skills/`（文件夹名保持 `quality-gate`；建议配 CLAUDE.md 强制自动触发） | [integrations/claude-code.md](integrations/claude-code.md) |
| Cursor | 原生读 `.agents/skills/`；或 prompts/ 配置为两个自定义 Agent | [integrations/cursor.md](integrations/cursor.md) |
| Codex / AGENTS.md 约定工具 | 原生读 `.agents/skills/`；或 prompts/ 内容并入 AGENTS.md / 自定义指令 | [integrations/codex.md](integrations/codex.md) |
| 任意其他工具 / 纯对话 | 把 prompts/ 当角色卡、SKILL.md 当操作手册手动走流程 | [integrations/generic.md](integrations/generic.md) |

> 手动拷贝时**文件夹名保持 `quality-gate`**（与 SKILL.md 的 `name` 一致），否则部分工具无法识别。

> **已安装过的仓库升级**：重跑同一条 `npx skills add ospops/quality-gate` 覆盖更新
> （手动拷贝的重新拷贝），并**同步替换** CLAUDE.md / Project Rules / AGENTS.md 中的
> 触发规则文本——旧版无门槛规则是"一问就触发"的主要残留来源。

最小可用三步（任何工具通用）：

1. 开发前：把 `prompts/requirement-adversary.md` 发给一个独立会话/子代理 + 你的需求 → 收《需求漏洞清单》→ 修正需求；
2. 开发后：跑自测门 → 把 `prompts/implementation-adversary.md` + 改动清单发给另一个独立会话/子代理 → 收《发现表》；
3. 修复 🔴/🟠 → 重复第 2 步 → 全清后按 `examples/report-template.md` 归档报告并宣布"已通过对抗审查"。

## 场景速查（我这样说，质量门会怎么走）

### 会走完整流程（开发回合）

| 你说 / 场景 | 行为 |
| --- | --- |
| 新功能 / 修 bug / 重构 / 写脚本或测试 | 阶段 A 审需求 → 开发 → 自测门 → 实现对抗 → 修复循环至 PASS，才汇报"已实现且已通过对抗审查" |
| "修一下这个报错"（先诊断后修） | 阶段 A 降级为一句方案自检（需求 = 缺陷现象 + 根因），其余流程完整 |
| "加个打点/监控，部署后观察"（点名交付） | 是开发回合（要上生产的改动不过裸门）；阶段 A 按点位清单降级，实现对抗重点攻日志安全与性能 |
| 单函数/局部重构（"太乱了收拾一下"） | 不算机械性任务（目标形状有解释空间），照常审需求 |

### 走减负流程

| 你说 / 场景 | 行为 |
| --- | --- |
| "审下这段代码""这个文件有没有问题/安全吗""帮我看看""把把关" | **审计模式**：对象是代码派实现对抗、是 PRD/方案派需求对抗；片段免自测门（diff/PR 审计仍跑一次基线）、免修复循环，发现表对话直返，要修才转修复循环（用户要求归档亦落盘，终态"已审计"） |
| 手动 `/quality-gate <范围>` | 同上，审计模式 |
| "审下这个 PR，红的直接修掉不用问我" | 审计模式 + 预授权修复 → 发现 🔴/🟠 直接进修复循环，不反问 |
| 琐碎修正（≤1 文件、<10 行、不涉逻辑/数据写入/权限/并发；多行错别字/文案同享豁免） | 阶段 A 与 C 全免，汇报时注明"已降级 + 理由" |
| 依赖升级 / 批量重命名 / 格式化（机械任务） | 免阶段 A（风险交给实现对抗） |
| 全仓格式化 / 注释翻译 / 展示文案批量替换（零语义改动） | 再免实现对抗与报告，仅跑自测门；标识符重命名**不**属此类 |
| 纯文档改动（README/注释性文档） | 免阶段 C |

### 不触发（直接正常回答，也不多一句"已跳过"）

| 你说 / 场景 | 行为 |
| --- | --- |
| 纯提问 / 概念解释 / 闲聊 / 工具用法咨询 | 直接回答 |
| "为什么崩""哪儿慢"（排查诊断） | 只诊断；本回合中途转为动手修复才从那一刻进入流程 |
| 模型为排查**自主**写的插桩/打点（含临时留在仓库） | 属诊断回合，不触发 |
| 用完即弃的 repro / demo / 临时脚本（无论写在哪，含仓库树） | 为回答问题而写，不触发；决定留作交付才进入 |
| 聊天里要代码片段 / 正则 / 配置示例（不落仓库） | 直接给 |
| 通用知识问答（"JWT 放 localStorage 安全吗"——不指向仓库内对象） | 普通问答，不派审计 |

### 衔接与特殊情形

| 你说 / 场景 | 行为 |
| --- | --- |
| 任务中途"再加个字段"（增量需求） | 只补审增量，不重跑全量需求对抗 |
| "改 A、改 B、改 C"一批交回 / 同一任务多次微调 | 合并为**一次**审查与一份报告 |
| 被打断后问"改完了吗" | 可先答一句状态（"代码已写完，正在补对抗审查"），补走该交付的阶段 C 后再宣告完成 |
| 循环被轮次上限叫停后说"继续" | 解除上限追加 1 轮（累计计数不清零，再触顶即终局） |
| 开发回合以零改动收场（诊断为环境问题/非 bug） | 汇报结论即可，免 C 免报告 |
| "不用审" / "先别跑测试" | 用户明确豁免，注明后跳过 |
| 重启/隔天/换人后继续未完成交付（"继续昨天那个"、"还有没做完的？"） | **冷启动续作**：按状态行前缀检索报告目录找"进行中"报告——改动对得上 → 从状态行"下一动作"继续，已完成轮次不重跑；"终局·分歧"点名指认、或光杆"继续"且唯一时续作；对不上 → 确认一次收口或保留（孤儿让位）；查无 → 完成性提问按挂起交付口径作答、开发话语按全新任务走 |

> 本表为速查；完整判定规则以 SKILL.md 第 0 步（预筛选）、0.1 冷启动续作细则、
> 0.2（时机与降级）与阶段 C（审计模式）为准，如有出入以 SKILL.md 为权威。判定拿
> 不准时一律按普通问答放行——漏审可随时 `/quality-gate <范围>` 补救。

## 报告规范

- 文件名：`YYYYMMDDHHIISS-ai-report-<主题slug>.md`（日期时间 = 报告（骨架）创建时刻、
  精确到秒；slug 用 ASCII，如 `20260924153045-ai-report-export-orders.md`）；
  极端重名（同一秒重复生成）时追加 `-2`/`-3` 序号，不覆盖既有报告；
- **状态行**：报告首部维护 `状态：进行中·第 N 轮·下一动作=…`（骨架先行建立、每轮更新；
  终态枚举：PASS / PASS·免审 / 终局·分歧（第 N 轮） / 已审计 / 已审计·待修 N 项 / 作废·原因）——
  这是断点续作（重启/隔天/换人接手）的唯一交接锚点；
- **基准 commit**：报告首部记录（未开发记当时 HEAD；迟建记开发开始前的提交，无法确定
  宁早勿晚并注明"基准估计"；非 git 写"非 git"）——冷启动"对得上"判定的锚定依据，
  "触发改动"须列出改动文件清单；
- 目录：跟随目标仓库报告惯例，默认 `docs/reports/`；
- 模板：[examples/report-template.md](examples/report-template.md)，填好的样例见
  [examples/report-example.md](examples/report-example.md)；
- 报告由主 Agent（而非审查者）撰写；复审逐轮追加记录（复审只验证上轮修复+回归，
  同一交付累计 5 轮上限）。

## FAQ

**为什么是两个角色而不是三个或七个？**
需求层与实现层各一个对抗者；实现对抗内部的七个维度（代码审查/边界/异常/数据/并发/安全/自动化测试）是同一角色的检查清单，不是独立 Agent——层级一致、维护最小。

**为什么审查者绝对不能改代码？**
裁判下场踢球必然既当运动员又当裁判。只读约束在提示词与工具权限两层同时生效（可写工具环境靠铁律）。

**没有测试/没有 git/没有需求文档的仓库能用吗？**
能。自测门缺哪类跳哪类并注明；非 git 以任务记录定位改动；无需求文档以任务描述为基准（报告标注）。

**用户只是提问、聊天也会触发整个对抗流程吗？**
不会。SKILL.md 第 0 步设有预筛选：仅当本回合将写/改代码或配置才进入流程；
纯问答、概念解释、方案讨论、读代码等非开发回合**立即整体退出**——不派对抗、
不写报告、也不多一句"已跳过"。三个自动触发模板（CLAUDE.md / Project Rules /
AGENTS.md）同样自带该门槛；讨论中途转为动手改码时，从动手那一刻补走阶段 A。
漏审可随时 `/quality-gate <范围>` 补救，因此判定拿不准时一律放行为普通问答。
唯一例外：被问及此前挂起交付的"完成"（如"改完了吗"）——先补走该交付的阶段 C
再宣告完成，否则"未过门即宣告完成"会击穿质量门本身。

**排查 bug、写个临时脚本验证算开发回合吗？跑一次要多久？**
排查/诊断以定位原因为目的——不算开发回合，整体退出；本回合转为动手修复时才进入，
且阶段 A 降级（需求 = 缺陷现象 + 根因）。用完即弃的 repro/demo 同样不触发；
用户点名"审下这段代码"则视同手动命令，只跑阶段 C。耗时上限也有约束：迭代轮次
只跑定向测试、全量留到 PASS 判定前（慢套件 1 次），实现对抗不重复跑全量套件、
只攻击本次改动波及面，同一任务的中途微调、同一批交回的多个小改动都合并进最终
一次阶段 C，与改动无关的基线既有失败注明后不硬修、也不为跑命令现场安装重型
依赖——小交付的典型开销是"一轮定向自测 + 一次对抗子代理"。

**手动 /quality-gate 或点名"审下这段代码"，也要跑完整流程吗？**
不必——**审计模式**按范围减负：纯片段/指定文件审查跳过自测门与修复循环，发现表
直接在对话返回，转修复或用户要求归档时才落盘报告；审计已有改动（diff/PR）只跑
一次基线，用户要求修复才转入交付门循环。另有三道防"一问就耗时"的保险：两个对抗
提示词自带前置校验（输入不是开发任务 / 无审查范围时一行退回，可拦住旧版无门槛
规则的误派）；环境依赖型测试（需 DB/密钥/外部服务而本地不具备）注明跳过不硬跑；
执行命令一律带超时，防止单条命令挂起拖垮整轮审查。
