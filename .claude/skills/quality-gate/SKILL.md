# 对抗式开发（自动质量门 · 工具中立版 · 主 Agent 执行协议）

> ⚠️ **第一动作是第 0 步预筛选**：本回合若非开发回合（纯问答、排查诊断、用完即弃的
> 验证代码——不会向仓库留下交付改动），**立即停止执行本技能**，直接正常回答；
> 以下全部流程仅在开发回合适用。

你是 Main Agent：写需求、写代码、汇总、修复的人。本技能把开发流程变成双层对抗闭环：

```
需求（任务）
   ↓
【需求对抗】requirement-adversary ── "这个需求有没有漏洞？"
   ↓
修正需求（Main Agent）→ 开发（Main Agent）
   ↓
自测门（类型检查 / 测试 / 构建，按仓库实际）
   ↓
【实现对抗】implementation-adversary
   ├─ 代码审查        ├─ 边界攻击        ├─ 异常攻击
   ├─ 数据攻击        ├─ 并发攻击        ├─ 安全攻击
   └─ 自动化测试
   ↓
汇总报告 → 发现问题？
   ├─ 是 → Main Agent 修复 → 重新实现对抗（回到自测门）
   └─ 否 → PASS → 才向用户汇报"已实现且已通过对抗审查"
```

**职责边界**：两个对抗角色**只读不写**，只返回文本结论；报告文件、需求修正、
代码修复、测试固化全部由你（Main Agent）完成。

**包结构（单文件夹即完整发布包，详见 README.md）**：

```
quality-gate/
├── LICENSE                       ← MIT
├── README.md                     ← 面向人类的说明（快速开始/理念/FAQ）
├── SKILL.md                      ← 本文件（编排协议）
├── prompts/
│   ├── requirement-adversary.md  ← 需求对抗提示词（唯一权威版本）
│   └── implementation-adversary.md ← 实现对抗提示词（唯一权威版本）
├── integrations/
│   ├── claude-code.md  ├── cursor.md  ├── codex.md  └── generic.md
└── examples/
    ├── report-template.md        ← 审查报告模板（复制即用）
    └── report-example.md         ← 填好的样例报告（对齐格式用）
```

## 执行形态（按当前工具自适应，流程与判定完全一致）

派对抗角色 = **先读取对应提示词文件全文，交给一个独立上下文执行**：

- 需求对抗 → `prompts/requirement-adversary.md`
- 实现对抗 → `prompts/implementation-adversary.md`

| 环境 | 执行方式 |
| --- | --- |
| 有子代理机制（如 Claude Code 的 Agent 工具、Cursor 自定义 Agent） | 派**通用**子代理，提示词=文件全文+本次范围（Claude Code 装了原生薄壳则直接按类型派）。**别用纯搜索型子代理**（如 Claude Code 的 Explore）跑对抗——其定位是定位代码而非审计，只会得到浅结果 |
| 有子代理、无只读类型 | 派通用子代理 + 提示词铁律一字不落 |
| 无子代理机制 | 新开独立会话贴提示词执行；或由你降级自审——每个角色开始前**重新通读**涉及文件（禁止凭实现时的记忆下结论），审查期间停用一切写操作，报告注明"降级自审" |

各工具具体配置见 `integrations/`（claude-code / cursor / codex / generic）。

## 第 0 步：触发判定

### 0.1 预筛选：本回合是开发回合吗？（先于一切动作执行）

判定只有一条：**本回合将向仓库写/改作为交付的代码或配置**（新功能、修 bug、重构、
脚本、测试、构建/依赖配置等）。仅凭用户消息与当前上下文一瞥判定，**不派子代理、
不读文件、不跑命令**——预筛选本身必须零开销，否则就失去了省时间的意义。

| 本回合性质 | 处理 |
| --- | --- |
| 纯问答 / 概念解释 / 方案讨论（不落码）/ 读代码问"这是什么、在哪" / 闲聊 / 工具用法咨询 | **整个流程立即退出**：不派任何对抗、不跑自测门、不写报告、也不向用户说明"已跳过质量门"（多余汇报同样是浪费） |
| 排查 / 诊断 / 性能分析（"为什么崩""哪儿慢"）——**你为定位问题自主**写的插桩/日志/打点（即便临时保留在仓库）同属此类；但**用户点名交付、要部署的打点/监控是开发回合**（目的就是产出交付改动），阶段 A 按转修复降级（需求 = 点位清单） | 自主插桩：整体退出；本回合内转为动手修复时，从动手那一刻进入 0.2（阶段 A 按"讨论/诊断转修复"降级，见阶段 A 第 4 条）；用户点名的可部署打点：进入 0.2，阶段 A 降级同上；临时插桩日后被当正式功能修改/依赖时，按新交付走 0.2 |
| 验证性一次性代码：repro 脚本 / demo / 临时验证（用完即弃——**无论临时写在哪，含放进仓库树**；以不作为交付保留为准） | 不算开发回合：为回答问题而写，不触发流程；若决定把其中改动作为交付保留，从那一刻起进入 0.2 |
| 将写/改代码（交付给用户） | 进入 0.2 |
| 讨论中途转为动手改码 | 从动手那一刻视为任务开始，补走 0.2 与阶段 A（方案已在讨论中协商一致时，按"讨论/诊断转修复"降级，见阶段 A 第 4 条） |
| 问答回合需汇报**此前挂起交付**的"完成"（如被打断后用户问"改完了吗"） | 不退出：可先答一句事实状态（状态同步不算完成宣告）；冷启动不记得有无挂起时，按"冷启动续作"细则发现——状态行显示实现已完成 → 补走阶段 C 再宣告"已完成"；仍在骨架期/开发中 → 按状态行"下一动作"续作；报告章节无法重建的注明"上下文丢失未复跑"（属收尾，不是新触发） |
| 续跑/恢复回合（**同会话**："继续""接着来"，针对进行中的流程） | 继承原回合判定与循环状态，不算新触发；若上一循环已因轮次帽停下，"继续" = 解除该帽追加 1 轮（累计计数不清零，再触顶即终局汇报；冷启动后对"终局·分歧"报告说"继续"同此语义，见细则） |
| **冷启动续作**（新会话/重启/隔天/换人；触发以话语为主——"继续昨天/之前那个"、盘点式"还有没做完的？"——工作区未交付 diff 仅作辅助线索） | 按"冷启动续作细则"执行；细则未命中 → 按全新任务走 0.2（用户未陈述任务先问一句，不空转） |
| 用户点名"审查 / 攻击 / 评估"某段现有代码、某份需求/设计文档、或对话中贴出的方案/片段（含"有没有问题""有没有隐患""这样写安全吗""帮我看看""把把关""行不行"等评估式问法；**无对象的通用知识提问不属此列**，走纯问答行） | 等同手动 `/quality-gate <范围>`：跳过阶段 A、只跑阶段 C（范围 = 用户指定，按"审计模式"减负执行，见阶段 C；对象是需求/设计文档时派需求对抗而非实现对抗），不走预筛选退出 |

拿不准时自问：**"本回合结束时，仓库里会不会有我产生的、要交付给用户的代码 diff？"**
（以排查/验证为目的的插桩、打点与临时脚本不算；命中上方"点名审查""挂起交付汇报"
或"冷启动续作（含交付盘点）"行的回合即使答案为"不会"也不退出——**这些行优先于
本问句**。）
不会 → 退出。误放行（漏审）可由用户随时 `/quality-gate <范围>` 补救，误触发
（问答跑了全流程）则纯属浪费——两类错误代价不对称，倾向退出。用户手动
`/quality-gate` 不受预筛选限制（显式指定即明确要审）。问答回合顺手做的微小清理，
只要满足下方"琐碎"客观线，按降级处理即可，不把整个回合升级为开发回合。

**冷启动续作细则**（本检查不属于预筛选：在判定为开发回合且进入 0.2 前，或命中
"'改完了吗'类完成性提问、'还有没做完的？'类**交付**盘点、'继续昨天/之前那个'类
点名续作话语时执行——同审计模式的例外；用户明确给出新任务（可执行的任务描述）→
直接 0.2 不查）：

- **锚点识别**：状态行忽略行首空白与列表符（`- `/`* `/`+ ` 及有序列表符）后以
  "状态：进行中·"开头才算进行中；终态判定同理（以"状态：PASS"等开头，行内括注
  不算终态值）；状态行存在但前缀不匹配（半角冒号/加粗等微偏）→ 视同无状态行旧
  格式，按补写升级处理（微偏报告默认不主动扫描，点名/盘点时才升级）。**扫描三重
  限定**：①仅报告目录（默认 docs/reports/，天然排除技能包与 examples）；②文件名
  必须匹配 `YYYYMMDDHHIISS-ai-report-<slug>.md` 模式；③仅报告首部首个"状态："行
  参与判定，正文/围栏内引用不算。扫描 = 收集全部命中的"进行中"报告，仅一份时
  取之，多份且未指认 → 按下条枚举（点名指认可按主题 slug 全目录检索）；
- **终态词表（统一枚举）**：`PASS` / `PASS·免审` / `作废·<原因>` /
  `终局·分歧（第 N 轮）` / `已审计`（含未修发现时 `已审计·待修 N 项`——可被点名
  续作：用户要求修复时点名翻回进行中转修，轮次与注明见下条）；
  "终局·分歧"仅点名指认、或光杆"继续"且目录中无其他可续作锚点时续作（= 解除轮次帽
  追加 1 轮，累计不清零；跨会话轮次从"复审记录"表恢复——**表为轮次权威**，与状态行
  冲突以表为准并更正）；无状态行旧格式报告由你依正文 + 实况补写升级，注明"状态行补写"；
- 多份"进行中"未指认 → 枚举给用户选，不擅续；仅一份时光杆"继续"视为指认；
  **进行中优先于终局**；同主题 PASS 与"进行中"并存 → 取"进行中"但提示用户确认
  （PASS 份可能是漏收口的陈旧锚点）；**交付盘点 → 呈现全部"进行中"与"终局·分歧"
  （供参考）并报状态待指示，不自动续作、不做对得上核验**；待修/作废报告可被点名
  翻回"进行中·第（表行数+1）轮"（注明"审计转修复"/翻回原因）；PASS 后返工/增量 →
  独立新报告，"触发改动"注明"接续 <旧报告文件名>"；
- **"对得上"判据**：报告"触发改动"所列**改动文件清单**中**至少两个文件（或同一
  路径前缀下的文件；清单仅一个文件且基准后存在触及它的自有提交时，单文件命中亦算
  ——≥2 门槛防的是 README/lock 类高频文件误配，不误伤单文件交付）**出现在"当前改动"（= 工作区 diff ∪ 基准 commit 之后的提交
  ——基准 commit 的记录规则见阶段 A 第 3 条与 C3 模板字段；无记录时以报告文件名
  时间戳比对提交时刻）中；**骨架期零改动**（状态行第 0 轮且清单文件无任何改动/
  提交痕迹）视为对得上——实况显示已开发/已提交则按实况优先补 C1；非 git 仓库以
  清单比对工作区文件（mtime 早于报告日期的不算；仍无法判定 → 视同孤儿走一次
  确认）；别人的提交/merge 混入按无关排除——"自己" = 本交付会话的 Main Agent 及
  其委托用户（本机 git 身份）的提交，squash/共享身份/Co-authored-by 不可分辨时不
  做作者推断、直落清单比对（单一高频文件 README/lock/配置的重叠仅作弱证据，明示
  后询问）——无关重叠不劫持，C2 范围同此排除并注明；
- **孤儿处置**：对不上的"进行中" → 确认**一次**（确认时列出报告时间戳/主题/改动
  清单供辨认归属；无法确认归属的只加标注不改终态）：收口为 `作废·对不上`，或保留
  并在状态行行尾（同一物理行，防格式化折行）追加 `（对不上·日期 用户确认保留）`。
  已确认保留/收口的孤儿：**打扰豁免 + 多份选一时降权让位**——点名指认永远可达；
  光杆"继续"且无其他锚点时列出该保留孤儿询问，不判"查无"；让位识别为关键词级
  （含"对不上"且含"确认保留"字样即可，日期格式不拘）；
- **状态行与磁盘实况矛盾 → 以实况为准**：按 C4 语义先补齐未做动作（沿用状态行轮次，
  复审完成即该轮结束），随即更正；
- 查无"进行中"：完成性提问先答事实（命中终态 PASS 报告亦直接答事实，不触发补 C
  分支）→ 用户表述开发意图才 0.2 → 明确质疑 PASS 才另立审计复核（旧报告不动）。

### 0.2 时机与降级

| 时机 | 动作 | 可跳过（汇报时说明原因） |
| --- | --- | --- |
| 新任务开始（拿到需求后、写代码前） | **阶段 A：需求对抗** | 琐碎小修正类任务；机械性任务（依赖升级、批量重命名/移动/格式化——需求无解释空间，风险交给阶段 C；**单函数/局部重构不属机械性**，目标形状有解释空间应审，拿不准时倾向不豁免） |
| 实现/修复完成、即将汇报"完成"前 | **阶段 C：实现对抗**（以一次交付为单位） | 纯文档改动（覆盖混合交付中的纯文档部分；纯文档回合预筛已放行）；用户说"不用审"；满足下方"琐碎"客观线的修正（≤1 文件、<10 行、不涉逻辑/写入/权限/并发——多行错别字/文案同享豁免）；纯空白/注释/展示文案的零语义批量改动（全仓格式化、注释翻译、文案替换——**标识符重命名不属此类**）：免派实现对抗、免落盘报告，仅跑 C1 自测门并注明（此类免 C，不建骨架；免 C 收场汇报口径 = "已完成（免对抗审查：<原因>）"） |

**"琐碎"的客观判定**（降级须在汇报中注明"已降级 + 理由"，不许凭主观感觉省流程）：
改动 ≤1 个文件、新增/修改 <10 行、且不涉及逻辑分支 / 数据写入 / 权限 / 并发
（例：错别字、注释、文案常量）。行数统计排除 lock 文件与生成文件
（其 diff 动辄上千行，不代表逻辑改动）。

- 配置了自动规则的工具（CLAUDE.md / Project Rules / AGENTS.md，模板见 integrations/）：自动触发；
- 未配置的工具：由你按上表主动执行；用户手动 `/quality-gate <范围>` = 审计模式（见阶段 C）：跳过阶段 A，按范围减负跑阶段 C；
- 开发回合以零 diff 收场（诊断为环境问题/非 bug、用户撤回）：汇报结论即可——阶段 C 无对象、免报告，不算降级、无需注明（已落骨架的按阶段 A 第 3 条收口为 `作废·零 diff`）。

## 阶段 A：需求对抗（开发前）

1. 按执行形态派出需求对抗，输入 = 任务描述 / 需求文档（PRD、README、issue，存在才读；
   超长文档只附关键节选，不整篇塞给子代理）；
2. 收到《需求漏洞清单》（🔴阻塞开发 / 🟠需澄清 / 🟡建议）后：
   - 🔴/🟠 → 你修正需求（改写任务理解、补 PRD、或向用户澄清），修正后可复审一轮；
   - 🟡 → 记录，进入开发；
3. 结论落盘：**将走完整阶段 C 的交付**创建**报告骨架**（命名/目录/模板规则同 C3）——
   阶段 A 结束时建（A 被豁免**且将走完整 C** 的任务于进入 C1 前建——可预见免 C 的
   任务不建；需求基准写任务描述 + 豁免注明），
   填"需求对抗结论"与需求基准指针（PRD/修正后基准的路径，或注明"基准为任务描述"），
   记录**基准 commit**（未开发记当时 HEAD；迟建记开发开始前的提交，无法确定**宁早
   勿晚**并注明"基准估计"——偏早可被排除梯兜住、偏晚不可恢复；非 git 写"非 git"），
   "触发改动"须列出改动文件清单；
   状态行置"进行中·第 0 轮·下一动作=开发"——开发中途被中断（重启/隔天/换人）时断点
   可恢复；交付中途转为豁免/放弃收场的，已落骨架必须收口：状态行置 `PASS·免审` 或
   `作废·<原因>`，不留"进行中"死锚点（放弃收场且工作区有残留 diff 时询问用户保留
   或回滚，不擅动；未答复即会话结束的，diff 保留不动）；
4. 两类免重跑的省时规则：
   - **增量需求**（任务中途"再加个字段"类）：只对增量部分补审，或并入当前交付的
     最终阶段 C，不重跑全量需求对抗；
   - **讨论/诊断转修复**：需求基准 = 已确立的结论（缺陷现象 + 根因，或与用户协商
     一致的方案），阶段 A 降级为一句修复方案自检，报告注明"转修复，阶段 A 降级"。
     适用三种情形：排查回合中途转修复；"修一下这个报错"类先诊断后修的单任务
     （诊断完成即确立需求基准）；方案讨论达成一致后用户说"就这么改"。

## 阶段 B：开发

按修正后的需求实现（正常工作流，无特殊约束）。

## 阶段 C：实现对抗（质量门）

**"一次交付"的判定**：你准备向用户宣告"已完成 / 可用"之时。同一任务的中途修复与
微调**不逐次触发 C**，合并进最终那次（C4 循环内"回到 C1"是同一次 C 的内部循环，不算新触发）。
同一批交回的多个小改动（"改 A、改 B、改 C"）也合并为**一次**审查与一份报告，不逐项跑 C。

**审计模式**（手动 `/quality-gate` 与用户点名/评估式审查时）——对象不是你本次的交付，流程减负：
- 分支判定可查一次 `git status/diff`（预筛选的零成本约束止于预筛选，此刻已进入流程）；
  被点名对象含**你未汇报的交付**时，优先按"挂起交付补走 C"处理，其余范围按本模式；
- 对象为需求/设计文档（PRD、方案）：派**需求对抗**（模式一）而非实现对抗，漏洞清单对话直返；
- 范围无仓库改动（贴出的片段、"这个文件有没有问题"）：跳过 C1 与修复循环，只派
  实现对抗做只读分析，发现表**直接在对话里返回**；
- 范围为已有改动（diff / PR / 未提交变更）：C1 只跑一次**审计段**基线（转 C4 后的
  回归按省时策略定向跑，不受"只跑一次"限制），发现先汇报，**用户要求修复才转入
  交付门循环（C4）**，不自行开修（用户在原始指令中已预先授权修复的，视为"要求修复"
  已成立，直接进 C4）；
- 报告规则三分支统一：默认对话直返；仅转修复进 C4（报告是循环锚点）或用户要求
  归档时落盘，命名/模板同 C3；审计他人改动的收尾口径 = "已审计 X：🔴×n 🟠×n…"
  （按预授权修复并复审通过时附注），不说"已实现"。

### C1 自测门（不过先修，不派审查）

按仓库惯例选择质量命令（探测 package.json scripts / Makefile / pyproject.toml / Cargo.toml /
pom.xml / go.mod / 脚本目录等，缺哪类跳哪类并在报告注明"无此项"）：

```
静态检查（typecheck / lint）→ 测试（test / check）→ 构建（build / compile）
```

**省时策略（慢仓库必读）**：迭代验证（含 C4 每轮回归）一律**定向优先**——测试跑与
改动文件相关的子集，静态检查/构建限定改动所在包/模块（monorepo 尤其如此），全量
留到 PASS 判定前跑（口径见"快速参考·稳定性"）；全量构建单次过慢（如 >10 分钟）
且与本次改动无直接关联时，用等价定向目标替代或注明跳过。需外部环境（DB / 密钥 /
隔离网络）而本地不具备的测试，注明跳过**不硬跑**；执行命令一律带超时——默认
≤120 秒，全量套件终跑与已知慢的定向命令可放宽至 ≤15 分钟（放宽须注明），
防止挂起拖垮整轮审查；不为跑质量命令现场安装重型依赖或
拉起外部服务（容器/DB 等），环境未就绪即注明跳过。**基线既有失败**（与本次改动
无关、仓库本来就红）注明后不硬修，只要求"不新增失败"。**flaky 甄别**：同一命令
连续 2 次失败且无法归因于本次改动（或单次重跑即过的间歇红）→ 按 flake 注明后
放行派审，不计入修复循环。**单轮预算**：每轮自测门命令累计 ≤30 分钟，超出则缩小
定向范围/抽样并注明；终跑超时且无法归因本次改动 → 注明后不回 C1、不计轮次
（超时 ≠ 翻红 ≠ flake）。一切省时选择必须在报告注明，不许静默缩水。

### C2 派出实现对抗

按执行形态派出实现对抗，提示词附：本次改动文件列表/摘要 + 仓库自定义攻击清单路径
（若仓库约定了此类清单则附其路径，存在才读）+ 输出要求（发现表 + 自动化测试结果 +
测试盲区）+ 本轮自测门已跑内容（定向清单/全量与否——复审轮注明"定向，全量待终跑"），
让对方不必重跑。审查范围仅限本次交付的改动；工作区既有无关改动（用户自有 WIP）排除
并在报告注明。同时做实现核对（模式二）时，输入附阶段 A 修正后的需求基准与已记录
不做的 🟡——核对以修正版为准，不重新解释原始需求。

### C3 汇总报告（由你写，不是对抗角色写；交付门路径骨架已建，此处补全——审计模式落盘时新建，状态行终态用"已审计"）

- **状态行（断点续作锚点，每轮必更）**：报告首部维护
  `状态：进行中·第 N 轮·下一动作=<具体动作>`（如"待 R3 复审 #3 修复"），
  终态改 `PASS` 或 `终局·分歧（第 N 轮）`——重启/隔天/换人靠它续作；
- **文件名规则（固定，全工具统一）：`YYYYMMDDHHIISS-ai-report-<主题slug>.md`**
  （日期时间 = 报告（骨架）创建时刻，精确到秒，如 `20260924153045`；主题 slug 用 ASCII：
  小写字母/数字/连字符；中文主题取英文关键词）；
- 目录：跟随仓库已有报告惯例，否则默认 `docs/reports/`（不存在则创建）；
- **重名防覆盖**：秒级时间戳下重名罕见（多为同一秒重复生成），一旦文件名已存在，
  追加 `-2`/`-3` 序号（或换更具体的 slug），不得覆盖既有报告——C4 复审要引用
  上一轮报告路径，覆盖即断审计链；
- 模板：`examples/report-template.md`（含需求对抗结论、实现对抗发现、自动化测试、
  汇总判定、复审记录五节）。

### C4 判定与循环

- 存在 **🔴/🟠** → 你立即修复 → **回到 C1**；重审派**新的**独立上下文（新子代理/新会话），
  附上一轮报告路径 + 本轮修复说明（git 仓库附 diff，否则列改动文件与要点）；
- **重审范围收窄**：复审只验证「上轮 🔴/🟠 是否已修复 + 修复是否引入回归」，
  **不做全量重新攻击**——全量攻击每轮都能挖出新发现，循环永不收敛；
- **总轮次上限**：同一交付累计 **5 轮**（复审记录表行数，初审计计第 1 轮）仍未
  PASS → 状态行置"终局·分歧（第 N 轮）"并停下向用户汇报分歧点（同一问题连续
  3 轮未收敛可提前停下汇报，不必等满 5 轮）；每轮在报告"复审记录"表追加一行并
  同步更新状态行（表为轮次权威）；
- 仅 **🟡/🔵** → 记录在案，可 PASS（用户明确要求修复时才修）；
- 全空 → PASS。

### C5 收尾（PASS 后才向用户汇报）

1. 高价值攻击用例由你固化进仓库测试套件（若有）；
2. 报告最终判定与状态行改 PASS 并归档；
3. 汇报口径 = **"已实现且已通过对抗审查"**，附报告路径与发现统计
   （🔴×n 🟠×n 🟡×n 🔵×n ｜ 需求 ❌×n ⚠️×n）。

## 快速参考

- 阶段 A 单派需求对抗；阶段 C 若同时做实现核对（需求对抗的模式二），可与实现对抗**并行**；
- **断点续作**：报告状态行是唯一交接锚点（骨架先行、每轮更新、终态收口，豁免/放弃
  也收口）；冷启动按细则以前缀检索找"进行中"报告续作（话语触发为主、无关 WIP 不
  劫持、孤儿确认一次后让位），不重跑已完成轮次；
- 手动 `/quality-gate` 与点名审查 = **审计模式**：片段审查免 C1、免修复循环、发现
  对话直返（转修复进 C4 或用户要求归档才落盘报告）；转修复才进交付门循环；
- 重审每轮用**新的**独立上下文，不复用旧结论（旧会话已丧失独立性）；
  复审范围收窄为「验证上轮修复 + 回归」，全量攻击只在首轮；轮次上限两条并列：
  同一交付累计 5 轮（初审计计第 1 轮），其中**同一问题连续 3 轮未收敛即可提前停下**
  向用户汇报分歧点，不必等满 5 轮；
- 稳定性：迭代轮次只跑定向测试（报告基线注明"全量待终跑"）；全量套件**仅在 C4
  判定无 🔴/🟠 后、C5 汇报前终跑一次**——快套件连续 3 次（3 连中 1 红 2 绿视为
  flake 通过），慢套件 1 次；终跑翻红且单次重跑即过/无法归因本次改动 → 按 flake
  注明放行（不回 C1、不计轮次），其余翻红才回 C1 计轮次；全量套件已知 >15 分钟
  或全局配置类改动无等价定向目标 → 终跑改用 CI 最近一次结果/定向子集替代并注明；
  无测试免此项；
- 可移植性：不预设语言/框架/包管理器/构建/测试/git/需求文档/AI 工具；
  提示词与模板全部在本包内（prompts/ + examples/），单一权威来源。
